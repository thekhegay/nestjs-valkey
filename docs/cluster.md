# Cluster

A lock lives at `<prefix>{<tag>}`, and the key's last fencing token at `<prefix>{<tag>}:fence`. The tag is the key with `%`, `{` and `}` escaped, so both keys always hash to one slot, whatever braces the key holds, and locks spread over the shards. (The documentation's Redis lock store increments one global counter next to the lock, which a cluster refuses with `CROSSSLOT`.) An idempotency record is one key, the documentation's layout. A prefix must not contain a brace, and neither must ioredis's `keyPrefix`, which applies on top of it: `ioredisRunner()` refuses a client whose `keyPrefix` has one.

Every script has to run on a primary. ioredis sends them there whatever its `scaleReads`. Give the stores a glide client that reads from the primary, glide's default: with `readFrom` set to `preferReplica` or an `AZAffinity` mode, glide marks every connection read-only, and after a planned failover (`CLUSTER FAILOVER`) it keeps sending the scripts to the demoted primary, which runs them as a replica and fails them (`Attempted to access a non local key in a cluster node`) until glide refreshes its slot map, up to a minute later. An application that reads from replicas through glide needs a second client for the stores.

While a slot migrates key by key (`MIGRATE`, what `valkey-cli --cluster reshard` does by default), the server refuses a script whose keys are not all on one side of the move, so `acquire()` of a lock that is not held, in that slot, fails with `TRYAGAIN` (glide) or `Too many Cluster redirections` (ioredis), and the job skips its tick; `renew()` and `release()` keep working. That lasts as long as the slot stays open: milliseconds for a slot of a few thousand keys, seconds for hundreds of thousands, and until `valkey-cli --cluster fix` after a reshard that was interrupted. On Valkey 9, `--cluster-use-atomic-slot-migration` moves a slot whole, and no call fails.
